Working boundary. The GEO Stack is Mason Nguyen’s working map for maintaining a legible public source system. It is not an industry standard, a required protocol, or a claim that a particular layer makes a model retrieve, cite, or represent a source.
01 / What the stack is

A maintenance map, not a visibility recipe.

The stack begins with the source itself, not with a machine-readable file. It organizes the material a person or system may need to identify, interpret, retrieve, and revisit a public claim: the page, access path, structured description, identity references, optional inventories, and maintenance record.

Google says the foundational practices for Search also apply to its AI features. A page needs to be indexed and eligible for a Search snippet to be eligible as a supporting link; Google also says that meeting requirements does not guarantee crawling, indexing, or serving.[1] The useful work is therefore preparation and maintenance—not a promise that a stack will produce a given answer-engine outcome.

Each layer should make the public record more understandable to a human reader. If it does not, it is probably a label in search of a purpose.

02 / The six layers

Build from the source outward.

03 / Source and access

The page has to carry the claim before the graph can clarify it.

A public page should answer a real question in readable text and make its provenance clear. It should show who is speaking, where the support comes from, whether a statement is a definition or interpretation, when the record was last reviewed, and what uncertainty remains. This is the first layer because every other layer refers back to it.

The access layer makes that source reachable. Google’s AI-features documentation points to familiar foundations: allow crawling, make content discoverable through internal links, provide important content in text, maintain a good page experience, and keep structured data aligned with what visitors can see.[1] These practices establish technical readiness; they do not establish authority by themselves.

On this site, the practical route is a stable canonical URL connected to related guides, the human Site Index, and the XML sitemap. The source-record guide explains the evidence and authorship layer in more detail.

04 / Structure and identity

Use markup and entity references as precise descriptions, not performative signals.

Google says structured data can provide explicit clues about a page’s meaning and may enable eligible rich results. It also says the markup should describe the page on which it appears, should not describe invisible content, and should favor complete, accurate properties over extensive but unreliable markup.[2] A good implementation is a faithful summary of the visible record.

Schema.org defines sameAs as a reference URL that unambiguously indicates an item’s identity.[3] That makes it a precise relationship: it is appropriate for a true equivalent or official reference, not for a neighboring interest, an aspirational association, or a page that merely uses the same name.

Google’s Organization documentation says that relevant organization markup can help it understand administrative details and disambiguate organizations. It recommends using properties that apply to the organization and can be useful to visitors, such as name, URL, logo, and applicable external profile references.[4] For the related site concept, see Knowledge Graph Authority and the Entity Authority glossary entry.

05 / External graphs

Reference ecosystems are not credentials.

Wikidata describes itself as a free, collaborative, multilingual secondary knowledge base that collects structured data, supports source-backed statements, and links information to other databases.[5] It can be a relevant external identity reference when a maintained, independently supported record belongs there.

It is not an automatic next step for every person, project, or organization. A Wikidata item has its own editorial rules, sources, community review, and maintenance burden. Creating a thin or weakly supported record simply to obtain a graph reference makes identity harder to evaluate, not easier. The same caution applies to every third-party profile: use it when it truthfully reinforces an existing public record.

06 / llms.txt

Inventory is useful only when its audience is real.

An llms.txt file can be a concise orientation document: a maintained list of important pages, terms, and boundaries for people or systems that choose to read it. It can improve the site owner’s own discipline by making its public research inventory explicit.

For Google generative Search, though, the boundary is clear. Google says it does not use llms.txt or other special AI text files for its generative Search features, and that such files neither help nor harm visibility or rankings in Google Search.[6] A supplemental file should never be sold as a Google citation mechanism.

This site keeps a scope note on llms.txt for that reason: an inventory can be maintained for the systems and people who use it, while the public HTML source, technical accessibility, and truthful entity record remain the primary work.

08 / Working order

Do the durable work in the order it depends on.

1

Build the source page.

Start with a consequential question, an answer, primary evidence, a named owner, and an honest claim boundary.

2

Make the route accessible.

Use a canonical URL, meaningful internal links, readable main content, and sitemap coverage. Test the actual delivered page.

3

Describe what is visible.

Add structured data that accurately reflects the page or organization. Validate syntax and correct mismatches.

4

Maintain identity references carefully.

Use only truthful, unambiguous official or equivalent references. Do not confuse a profile list with a knowledge graph.

5

Add optional inventories deliberately.

Publish llms.txt or similar files only when they serve an identified audience, and state their boundaries plainly.

6

Review the whole record.

Update sources, repair links, record observations, and separate observed platform behavior from causal claims.

09 / FAQ

Questions that keep the stack proportional.

Is the GEO Stack an industry standard?

No. It is a working map for this research site, built to keep the public source system inspectable. It does not describe a required protocol or a universal platform behavior.

Does llms.txt improve Google AI visibility?

No. Google says it does not use llms.txt or similar AI text files for its generative Search features. The file may be useful for a service or person that elects to use it, but it should not be represented as a Google requirement.[6]

Should every organization create a Wikidata item?

No. A Wikidata record should be truthful, independently supported, relevant, and maintained. It is not an automatic authority credential or a substitute for the organization’s own public evidence.

What should a team build first?

Start with the substantive source page. Structured data, entity references, and inventories should clarify an existing, maintained record—not compensate for an absent one.
